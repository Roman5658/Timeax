# Timeax: durable browser sessions

- Keep the existing public auth and workspace settings. Provision a new, independent `timeax_web_session_login` role (LOGIN, NOINHERIT, with the existing runtime-role restrictions). Apply `web-sessions.sql` after verifying the target project. Only this role may call `timeax_api.web_session`; it gets no table grants.
- Set `TIMEAX_WEB_SESSION_DB` through the hosting secret settings and `TIMEAX_WEB_SESSION_RPC_SHA256` to the digest returned by the SQL. Set both together after the DB preflight. Do not commit, print or send the password. Without both settings the existing in-memory deployment does not become durable.
- The server stores only a digest of the opaque browser token, the authenticated subject, and expiry. Provider access tokens, passwords, browser metadata and network data are not stored by this feature. Unfinished registrations still use a 15-minute memory-only proof; completed agency registration, password sign-in and login by email code use a 12-hour browser session when configured. Membership and roles are still resolved from their own server-side checks. Logout deletes only the session in that browser. Actual user deletion cascades, and deleted, banned or deactivated users cannot resolve a stored session.
- Before enabling publicly, verify an ordinary sign-in followed by refresh, closing and reopening the browser, one service restart, expiry, and successful logout; check another browser session remains independent. Remove the two settings together to revert to short, memory-only sessions; there is no need to drop the table to revert code.
