# Timeax attendance pilot: deployment gate

**Status: offline contract only.** `server/lib/nfc-shift-gate.mjs` has no HTTP route, no browser reader, no key provisioner, and no production store. Choosing a planned NFC mode does not enable NFC. Keep existing timekeeping paths and their policy checks unchanged until the pilot is explicitly activated. No QR attendance is in scope.

## Devices, readers and proof

- **Agency terminal with personal cards:** the restricted terminal credential identifies the agency and exact production. It must not be an employee login. A valid tap resolves a card binding to an active employee on the server; the terminal only receives Start or End, temporary authorization, and the final receipt. No roster, name, hours history or documents. A setup link, if added, is one-time, short-lived, approved by an agency admin for that exact site, and establishes only terminal authority.
- **Stationary point with employee phone:** the point identifies a site, not an employee. Resolve the employee from their signed-in session, and check the employee's active assignment to that agency at the site. In a shared factory, lookup and event ownership are both `(agency, site, membership)`, not only factory ID.
- **Native / live proof required:** on supported iPhones, including iPhone 14 Pro, an NDEF website link can show a system notification and open Safari when tapped. This is a navigation entry, not native NFC verification in a browser. [Apple background tag reading](https://developer.apple.com/documentation/CoreNFC/adding-support-for-background-tag-reading). [Chrome Web NFC](https://developer.chrome.com/docs/capabilities/nfc) documents Android NDEF access. Do not assume those browsers can perform an authenticated ISO 7816 tag session. Evaluate supported native readers with [Apple Core NFC](https://developer.apple.com/documentation/corenfc/nfciso7816tag) and [Android IsoDep](https://developer.android.com/reference/android/nfc/tech/IsoDep).
- **First-seen is not necessarily fresh:** the [NXP NTAG 424 DNA data sheet, §9.3](https://www.nxp.com/docs/en/data-sheet/NT4H2421Gx.pdf) distinguishes SUN/SDM NDEF messages from mutually authenticated live exchanges. A counter helps stop reuse, but cannot alone establish the age of a proof the server has never seen. Neither UID, static QR, static URL, a copied URL with an unused dynamic value, client clock, nor the browser's claim of proximity establishes freshness. For authoritative payroll use a tested authenticated exchange bound to the server's current challenge, or keep the feature off. No universal claim of physical presence: a personal card can be lent.

## Durable contract before wiring

1. From an authenticated worker or restricted reader credential, create a random short-lived challenge for its bound agency/site/reader/session; include membership only for a signed-in worker. Persist its digest, expiry and scope. Do not disclose worker IDs to a terminal. Reject disabled mode, expired enrollment or no active assignment at the first applicable stage.
2. The hardware verifier authenticates the live exchange for that exact challenge and returns a registered opaque card ID and unique receipt. Server owns validation keys (not in a URL, QR, browser, web bundle, or terminal-form input). Store only scoped registry IDs, not names/documents on tags; establish key rotation and lost-card revocation before use. Do not store raw tap payloads or key material in business/audit logs.
3. In **one durable transaction**, validate scope, effective (not planned) mode, card, reader, assignment and expiry. Consume challenge and uniqueness receipt and derive the only permitted next transition, scoped to agency, site and member. Issue a separate short-lived offer and store only its digest; bind it to credential, action, current shift version, and card. Reader UI sees no member ID.
4. In a second **single transaction**, recheck all mutable authority and expected shift state; consume the offer atomically with writing the canonical time event. Record actual server time. No independent shadow timesheet; archive/reporting must read the canonical shift data. A separate tap is required for end. Define corrections, access revocation and incomplete-shift recovery with auditability. Do not implement rounding or fallback authorization implicitly.
5. Review every legacy/manual/leader worker write path and its database permissions before turning a mode on. Do not allow an unreviewed path to bypass the effective mode. Keep the detached gate off without the verified hardware and scoped durable transaction store, or when its readiness checks fail. No production database or application route changes in this pilot contract.


## Self-service setup for agencies (after the pilot)

1. In the agency cabinet, choose the exact production and the planned NFC model. This must show setup status separately from active time recording. On a shared factory, each agency sees only its own cards and terminal bindings.
2. Choose **Add terminal**, **Assign personal card** (select one currently authorized worker on that site), or **Register stationary tag** (no worker selected). The agency owner gets a different short-lived setup link for each device/card for that role. The link expires after 10 minutes or after use. It is not evidence of attendance and does not enable the selected work-time policy.
3. Open the link on the authorized setup device, follow on-device instructions, and complete the native reader/card check. For a terminal link, approve and pair the intended device (use a managed native device key, not a general-purpose authentication session). For cards, use the authenticated reader/provisioner to verify the tag, establish site-scoped cryptographic material safely and run a read-back verification. Confirm the exact agency, production and role before finalizing. A failed or interrupted setup keeps the unit disabled; do not rely on partially provisioned cards.
4. Keep the setup token in the HTTPS fragment only until it can be removed from visible URL/history, then submit via a dedicated endpoint with no analytics/referrer leakage. The protected store saves only its digest, intent and expiry; terminal identity credentials are distinct. Claim revalidates admin/worker/tenant access, consumes the grant once and activates the registry binding atomically after successful native proof. The grant cannot be sent to an attendance endpoint because its type and purpose are different. No secret keys are placed in the link or browser.
5. Give agency admins a scoped status list (pending, ready, revoked), an explicit expiry for pending grants, and a revoke action for lost/mistaken links or devices/cards. Revocations and changes of assignment must invalidate existing offers immediately when checked by the real recorder. Use pagination/rate limits for multiple agencies; avoid a central manual provisioning queue. Backfill/cleanup of expired grants remains a background operational task, not an attendance or billing event.

`server/lib/nfc-provisioning-gate.mjs` is a detached contract for those distinct setup grants and binding revocation. Starting or finishing a shift is never a provisioning side effect. Both gates need a reviewed durable store, real device verification and an off-by-default deployment flag; helper tests do not establish device or database readiness.

## Physical acceptance checklist

- Validate actual card type and read/reader compatibility on the intended terminal phone and Roman's iPhone. Do not pick browser vs native for authoritative time capture until the hardware exchange can be verified end-to-end. First conduct a no-time-write device pilot, then a disposable-tenant staging test.
- Verify fresh start and separate fresh end. Test copied/static/expired evidence, replay, concurrent submissions, wrong reader/site and two agencies at the same factory, expired employment, revoked card, mode switched between offer and action, offline/restart and a lost terminal. Results must appear exactly once, in canonical shift history for the correct tenant; rejection must not create a shift.
- Check screen lock, user permission, browser/app handoff and screen-reader labels on actual devices. Confirm the terminal displays no roster or worker identity and that card, proof and setup secrets are excluded from logs and analytics.
