# Регистрация и вход на Lenovo

Основной проект: `C:\Users\V13\IdeaProjects\Timeax`. Отдельную копию для регистрации создавать не нужно.

- `npm.cmd run dev -- --port 5177` запускает этот проект. При наличии `.timeax-auth.local` регистрация и вход используют настоящую почту и базу Supabase, без списка разрешённых адресов в приложении.
- `npm.cmd run dev -- --port 5177 --real-auth` требует настроенный серверный файл и прекращает запуск, если его нет. Без настроек обычный запуск показывает сайт, но не принимает регистрацию.
- Регистрация: `http://127.0.0.1:5177/register/agency`. Повторный вход: `http://127.0.0.1:5177/login`. Сайт доступен только на самом Lenovo; на публичный домен эта команда ничего не выкладывает.
- Подтверждение почты не выдаёт права. Через этот маршрут можно подать заявку агентства и увидеть её после повторного входа. Это не подтверждает работу кабинетов.

## Что нужно до первого письма

1. В текущем Supabase проверка `Before User Created` направлена на старый закрытый сервис Render. Её нужно заменить согласованной защитой публичной регистрации, а не отключать вслепую. Проверить, что добавление аккаунта по email не открывает таблицы и не выдаёт роли, а также сверить SMTP, шаблон одноразового кода и лимиты.
2. Для заявки нужен только `timeax_pending_registration_login`: на 26 ноября у роли есть разрешение на две функции заявки, но вход запрещён. Не включать остальные роли и не выдавать лишних разрешений.
3. Скопировать `server/operator/local-auth.env.example` в `.timeax-auth.local` в корне проекта. Указать хост Session Pooler, значение CA (PEM с литеральными `\n`), пароль узкой роли, длину кода и проверенные хэши функций. Публичный ключ берётся из `.env.local`, если не задано переопределение. Секреты не отправлять в чат и не добавлять в Git.
4. После подготовки пользователь сам запрашивает первое письмо в Timeax. Проверка: регистрация с разных ящиков, выход, повторный вход и отсутствие доступа к чужой заявке. Автотест подменяет почту и хранилище и не доказывает доставку настоящего письма.
